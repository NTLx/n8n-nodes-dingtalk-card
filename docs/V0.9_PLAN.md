# v0.9.0 Production Hardening plan

## Objective and boundaries

v0.9 hardens the existing v0.8 contract. It adds no node operations, interaction families, or general DingTalk API coverage. Form and Selection callbacks remain deferred. The work does not promise durable deduplication or exactly-once delivery and does not require a production-instance change.

## Evidence-based support matrix

The n8n npm installation documentation currently specifies Node.js 20.19 through 24.x inclusive ([official npm installation docs](https://docs.n8n.io/deploy/host-n8n/install-options/install-with-npm.md)). Production acceptance recorded in [VERIFICATION.md](VERIFICATION.md) identifies n8n 2.44.6. The declared package compatibility target is therefore the stable n8n 2.44 line, tested through its `n8n-workflow` package at the lowest and highest published patches currently available, 2.44.0 and 2.44.2.

| Node.js | n8n 2.44.0 (`n8n-workflow`) | n8n 2.44.2 (`n8n-workflow`) | Runtime support claim |
| --- | --- | --- | --- |
| 20.19.0 | Local pass; CI gate configured | Local pass; CI gate configured | Supported for packed-plugin contract |
| 22.x (local 22.23.4) | Local pass; CI gate configured | Local pass; CI gate configured | Supported for packed-plugin contract |
| 24.x (local 24.22.1) | Local pass; CI gate configured | Local pass; CI gate configured | Supported for packed-plugin contract |

Node 24 is the contributor/build baseline: it performs clean dev dependency installation, lint, typecheck, build, the full test suite, package verification, and production dependency audit. CI then installs the packed artifact with production dependencies only and checks package registration and callback normalization on every listed Node/`n8n-workflow` pair. The isolated install uses npm `--legacy-peer-deps` because unrelated full-n8n transitive peer ranges conflict (for example, Stagehand 1.14 requires OpenAI 4 while the n8n graph resolves OpenAI 6); it still installs the exact packed plugin and requested `n8n-workflow` version. The same six packed-artifact checks passed locally on Node 20.19.0, 22.23.4, and 24.22.1 against `n8n-workflow` 2.44.0 and 2.44.2. Installing `n8n-workflow` on Node 20/22 reports an engine warning for its transitive `isolated-vm@7.0.1` (`>=24`), but package registration and callback normalization pass. This gate covers the plugin's loaded runtime path; it does not establish that unrelated expression-runtime/isolated-vm code works on Node 20/22. The prior CI run stopped on the unrelated ERESOLVE peer conflict; CI must pass on the corrected candidate commit.

This isolates plugin runtime support from dev-only tools: it makes no claim that the build/test toolchain supports Node 20 or 22. The matrix does not imply testing every patch of Node 22/24, every n8n patch, n8n Cloud, other n8n major/minor lines, or a full n8n server instance. Node versions below 20.19 and Node 25+ are unsupported. n8n versions outside stable 2.44.x are unsupported pending matrix evidence. The 2.44.6 production instance is recorded as connected-instance evidence, not re-tested as part of this local-only stage.

The package `engines.node` is `>=20.19.0 <25`, matching the official npm-install runtime range. All six packed-artifact matrix combinations passed locally; CI repeats them on the candidate commit. If a CI combination fails, keep the smallest contiguous range supported by passing combinations and state the reason here; do not weaken the CI matrix to manufacture a claim.

## Executable regression gates

- Stream tests assert exact-topic filtering, immediate empty 200 ACK before one workflow emit, malformed callback ACK behavior, duplicate ACK with one emit, TTL expiry, bounded eviction, and replay after stream reconstruction. Because the cache is in memory per stream instance, an actual process restart also starts with an empty cache.
- Lifecycle tests assert bounded reconnect backoff, fresh gateway lookup, stop/deactivation cleanup during pending lookup and open socket, timer cancellation, lock release, and safe handling of connection and send failures.
- Saved workflow compatibility uses the shipped inactive [interaction fixture](../examples/card-interaction.workflow.json): node type identifiers, type version, Trigger-to-Update connection, callback `outTrackId` expression, and manifest registration are asserted in `test/stream.test.cjs`.
- The replay boundary remains process-local. A duplicate `messageId` is suppressed only within one live process and the in-memory TTL/bound; restart, multiple workers, cache expiry, or cache eviction can allow replay. Workflows needing durable business idempotency must use durable workflow-owned state.

No acceptance step mutates the n8n database or internal community-node directories. No production n8n instance is changed in this hardening stage.

## Security, privacy, and operations review

See [Compatibility, security, and operations](COMPATIBILITY_SECURITY_OPERATIONS.md). Package verification scans published examples and verifies the built packed artifact and registration; example secret-pattern checks reject credential-shaped field names and common token formats. Raw callback data remains enabled by default for v0.5 compatibility, so operators must treat it as potentially sensitive execution data and disable `includeRawData` when downstream legacy consumers do not require it.

## Install, migration, and downgrade

Use the self-hosted Community Nodes GUI lifecycle described by n8n: install `n8n-nodes-dingtalk-card@<version-or-dist-tag>`; use the **Update** action for latest; uninstall then reinstall a selected version to upgrade to a specific version or downgrade. A dist-tag is resolved at install time and is not a continuing subscription. Never mutate n8n database rows or internal community-node install directories for acceptance.

v0.9 retains v0.8 node identifiers, existing operations, saved-workflow parameter names, output fields, callback opt-in, and process-local dedupe semantics. The fixture gate above is the reproducible backward-compatibility check. From v0.8, use the supported GUI update path and inspect active workflows after installing; no manual workflow migration is expected. Keep a deployment backup and use n8n's documented recovery procedure if the n8n upgrade itself involved database migrations.

## Release-ref policy and completion criteria

Package metadata is prepared as `0.9.0-beta.1`, and only the exact `v0.9.0-beta.1` prerelease tag maps to the beta channel. This plan does not authorize creating that tag, publishing npm, creating a GitHub release, or changing production n8n. Publication readiness requires the full local gate set, passing CI matrix on the candidate commit, and a final reviewed diff. Form and Selection stay deferred; no general DingTalk API expansion is included.
