# v0.6.0-beta.1 candidate plan

## Frozen v1 contract (universal-v1)

This is the implementation boundary for the first controlled A2UI mode. It is plugin-generic and additive. It adds Card Data Mode `a2ui` to Create & Deliver and Update, with the required JSON field `a2uiDescriptor`. It does not change Form, JSON, Presentation, streaming, callback normalization, or raw request-body behavior.

The descriptor is an object with exactly these fields: `version`, `profile`, `title`, optional `summary`, `tone`, `blocks`, optional `actions`. `version` is exactly the string `"1"`; `profile` is exactly `"universal-v1"`; unknown fields are rejected. `tone` reuses the Presentation enum `neutral`, `info`, `success`, `warning`, `danger`.

Limits and shapes:

- `title`: non-empty string, at most 200 characters. `summary`: string, at most 1000.
- `blocks`: required, 1–12 blocks. Each block has only the fields shown below; other fields and types are rejected.
- `{ "type": "text", "text": string }`, text at most 1000 characters.
- `{ "type": "keyValue", "label": string, "value": string }`, label non-empty and at most 100 characters; value at most 1000.
- `{ "type": "list", "items": string[] }`, 1–20 strings, each at most 300 characters.
- `actions`: optional array, at most one action; action shape is `{ "type": "request", "id": string, "label": string, "params"?: object }`. Unknown fields and action types are rejected. ID matches `[A-Za-z0-9_.:-]{1,64}`; label is non-empty and at most 100 characters.
- `params` has at most 20 keys. Each key matches `[A-Za-z0-9_.:-]{1,64}` and each value is only a string, finite number, boolean, or null. Parameter JSON is compact and keys are sorted before serialization.

The descriptor maps only to string-valued `cardParamMap` variables: `a2uiVersion`, `a2uiProfile`, `a2uiTitle`, optional `a2uiSummary`, `a2uiTone`, `a2uiContent`, and `a2uiActionVisible` (`"true"` or `"false"`). If an action exists, it also maps `a2uiActionId`, `a2uiActionLabel`, and optional `a2uiActionParams`. Content is deterministic plain text: text unchanged; key/value as `label: value`; list entries as `• item`; blocks separated by one newline. Markdown and HTML are not interpreted. No arbitrary card JSON, URLs, HTML/code fields, component/template/API selection, scripts, external calls, or executable content are accepted.

No `flowStatus` is emitted. The candidate template profile is NORMAL; no AI-card host assumption is made. A Create & Deliver descriptor containing an action requires `enableStreamCallbacks === true`; otherwise execution fails with `CardError` before any API request. Update maps descriptor data only: callback routing is fixed when the card is created, so Update does not enable callbacks.

## Candidate sequencing and acceptance

Implement the pure mapper and node boundary first, then docs/examples and local quality/release gates. No router, business state, deduplication, or LLM behavior is in scope. The official examples repository was inspected at `https://github.com/open-dingtalk/dingtalk-card-examples` (main tree; `app/card_templates` contains `多 Tab 页.json` and `智能回复.json`). Both assets use editor schemaVersion `3.0.0` but export `type: "im"`, `mode: "card"`; the former's component map includes `Loop` and `Input`. No NORMAL template matching the fixed header/content/request-button skeleton was found or verified. Therefore this candidate ships no invented import asset. Exact variable/action binding is in [A2UI.md](A2UI.md); visual and live template acceptance remains pending.

Package verification establishes code/package registration only. Production acceptance still requires a user-published template with the contract variables, template visual inspection, live Create & Deliver and Update, and a real callback click through Stream Trigger for an action-enabled card.
