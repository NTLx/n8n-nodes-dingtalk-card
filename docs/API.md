# API contracts checked 2026-10-24

## Controlled A2UI (stable v1 plus additive v2 candidate)

Form input on Create & Deliver or Update can select Card Data Mode `a2ui` and provide `a2uiDescriptor`. Stable `version:"1"` / `profile:"universal-v1"` keeps its frozen fixed-variable contract and accepted request-action callback path. The v1.1 candidate adds `version:"2"` / `profile:"universal-v2"`, which maps the published wide notification/report contract to string-valued `cardParamMap` fields for Markdown hierarchy, four KPI cells, validated clickable HTTP(S) links, footer metadata, and fixed `config={"autoLayout":true}`. See [A2UI.md](A2UI.md), the [v0.6 plan](V0.6_PLAN.md), and the [v1.1 plan](V1.1_PLAN.md). v1 Create with an action still requires Stream callbacks enabled; v2 URL links are navigation links, not request callbacks. Update maps data and does not enable callback routing. The plugin does not hard-code or publish DingTalk template IDs.

## Presentation Card Data Mode (v0.4.0 development)

For Form input on Create & Deliver or Update, Card Data Mode `Presentation` accepts the v1 descriptor documented in [PRESENTATION.md](PRESENTATION.md) and produces existing `cardData.cardParamMap` string values. It is opt-in; Card Data Form/JSON and whole-body Input Mode JSON contracts are unchanged. This mode is a stateless adapter and does not ship templates, render components, route actions, or enforce status transitions.

Primary documentation was fetched from current DingTalk documentation pages and their published backing content at `https://icms-document.oss-cn-beijing.aliyuncs.com/zh-CN/dingtalk/{namespace}/topics/{slug}.html`. The backing URL is how the current documentation frontend renders the body; it is not an application endpoint. That documentation check did not make authenticated calls; the later connected-instance live E2E is recorded below.

| Purpose | Method and path on `https://api.dingtalk.com` | Verified contract |
| --- | --- | --- |
| Enterprise internal app auth | `POST /v1.0/oauth2/accessToken` | JSON `{appKey,appSecret}`; response `{accessToken,expireIn}` (seconds). No token header on acquisition. Cache tokens per app. |
| Create & Deliver | `POST /v1.0/card/instances/createAndDeliver` | Required `cardTemplateId`, `outTrackId`, `cardData`, `openSpaceId`; matching delivery models. `cardData.cardParamMap` is string-to-string. Response `{success,result:{outTrackId,deliverResults:[{spaceType,spaceId,success,carrierId,errorMsg}]}}`. Check every delivery result. |
| Update | `PUT /v1.0/card/instances` | Required `outTrackId`; `cardData`, `privateData`, `cardUpdateOptions:{updateCardDataByKey,updatePrivateDataByKey}`, `userIdType`. Response `{success,result}` where result is boolean. |
| Streaming Update / Finalize | `PUT /v1.0/card/streaming` | Required `outTrackId`, `guid`, `key`, `content`; optional `isFull`, `isFinalize`, `isError`. Response `{success,result}` where result is boolean. |

Every card request uses **`x-acs-dingtalk-access-token`**, JSON body, and HTTPS. These are Card Platform endpoints, not the older robot interactive-card APIs.

Primary references:

- [Enterprise app token acquisition](https://open.dingtalk.com/document/orgapp/obtain-the-access_token-of-an-internal-app)
- [Create and deliver cards](https://open.dingtalk.com/document/orgapp/create-and-deliver-cards)
- [Update card](https://open.dingtalk.com/document/orgapp/interactive-card-update-interface)
- [AI streaming update API](https://open.dingtalk.com/document/isvapp/api-streamingupdate) — despite the URL namespace, the permission table explicitly includes enterprise internal apps.
- [Streaming tutorial](https://open.dingtalk.com/document/orgapp/typewriter-effect-streaming-ai-card)
- [Official Python SDK card helper](https://github.com/open-dingtalk/dingtalk-stream-sdk-python/blob/main/dingtalk_stream/card_replier.py) corroborates header, update/streaming paths and payload fields. The published Alibaba Cloud `@alicloud/dingtalk` 2.2.48 SDK `src/card_1_0/client.ts` corroborates the combined create/deliver path, response models and methods. Neither SDK is a package dependency.

`outTrackId` is supplied by the caller and identifies a card. A new template/data card needs a new ID; repeating Create with the same ID does not guarantee deduplication/upsert and does not generally update data. The node generates a UUID when Create & Deliver receives an empty ID; it is stable only within that execution, so a rerun may use a different ID. For replay correlation, derive and preserve a caller-controlled ID from a stable business/event key (for example, order ID plus immutable event ID), never from a random per-attempt value. Verify whether the card or delivery already exists before replaying an ambiguous failure. If the card exists, use Update. The [stable Create & Deliver recovery example](../examples/stable-create-and-deliver.retry.json) shows the ID expression and branches.

`openSpaceId` follows `dtv1.card//SPACE_TYPE.spaceId` and supports semicolon-separated spaces in the official combined API. In Form mode, **Group Chat** Space ID is the group's `openConversationId`; **Robot Direct Message** Space ID is the recipient's staff `userId` (with `userIdType=1`). Neither is a webhook URL. Guided group delivery maps to `IM_GROUP` + `imGroupOpenSpaceModel` + `imGroupOpenDeliverModel.robotCode`; guided direct-message delivery maps to `IM_ROBOT` + corresponding models + `spaceType=IM_ROBOT` and `userIdType=1`. Guided `robotCode` is optional for both targets: blank/missing (including whitespace-only) resolves to `appKey` (Client ID / AppKey) from the bound `dingTalkCardApi` credential at execution time, for the application's own enterprise robot. A nonblank override is sent unchanged. This only supplies the existing delivery-model field; endpoint, models and other request fields are unchanged. Whole-body JSON receives no such default. The resolved credential value is not added to execution output, logs or errors. Advanced fields are available through whole-body JSON, not guessed by this package.

`guid` is the streaming request's idempotency identifier. `isFull=true` replaces content, false appends; Markdown requires full, syntactically complete content. Official guidance limits content to 1 K per request and 10 K in total. The API does not expose a universal “finalize endpoint”: completion uses `isFinalize=true`, while error uses `isError=true`. The helper selects exactly one terminal flag and still supplies the required key/content/GUID. It does not force template-specific `flowStatus` values.

The documented Create & Deliver response nests failures under `result.deliverResults`. Defensive detection also handles `result:[{success:false,...}]` delivery-model responses. The latter is compatibility handling, not a claim that the combined endpoint's documented schema changed. `success:false`, `result:false`, nonzero `errcode`, or non-success `code` are errors even on 2xx. Server messages are not copied into execution errors. Some deliveries may already succeed before a partial failure; errors advise inspection rather than blind replay.

Outbound node errors use a normalized safe detail object: `code`, `category`, `retryable`, `mayHaveSucceeded`, and optional validated `httpStatus`. Categories are `validation`, `authentication`, `network`, `http`, `business`, `incomplete`, or `internal`. Continue On Fail retains its existing `error` string and adds this object as `errorDetails`, preserving operation, identifiers, success flag and paired-item linkage. Thrown errors remain item-indexed `NodeOperationError`s with safe category and replay guidance in the description. Original exceptions/causes, response bodies, server messages, request/card data, credentials and tokens are never retained in the normalized details.

`retryable` means the operation is safe for automatic replay, not merely that a human might retry later. Only transient token-acquisition failures and explicit invalid-token rejection are marked retryable; the latter retains the existing single auth refresh/replay with the identical write body and identifiers. That one internal refresh is the only automatic write replay. Other write retries remain workflow/operator decisions after verifying whether the write took effect. Network/timeout and HTTP write failures, business rejections, incomplete responses and partial deliveries are non-retryable; ambiguous write failures and partial/incomplete results set `mayHaveSucceeded: true`. Token-acquisition failures occur before the card write and set it false. Unexpected internal failures are not represented as network/write ambiguity.

Auth cache is bounded and process-local. Workers/restarts can fetch additional tokens. Explicit recognized invalid-token codes permit one auth refresh/replay; other errors never automatically replay writes. There is no distributed retry/idempotency database. The v0.2.0-beta.1 prerelease adds the separate Card Trigger transport below.

## Tooling decision

The [official n8n starter](https://github.com/n8n-io/n8n-nodes-starter) and [CLI guide](https://docs.n8n.io/connect/create-nodes/build-your-node/using-the-n8n-node-tool.md) were checked. The package adopts the official CLI, scripts, strict node registration, peer dependency and ESLint conventions in place. Programmatic execution serves the required centralized auth/partial-failure/error behavior; payload construction is pure and tested. There are no starter product nodes.

## Public default AI template — connected-instance live E2E

On 2026-10-24, a real connected n8n 2.44.x runtime with a DingTalk enterprise app completed group Create & Deliver → Update → Streaming Update → Finalize → Update(FINISHED), using public template `02fcf2f4-5e02-4a85-b672-46d1f715543e.schema` and blank guided Robot Code fallback. Initial streaming with `key: "content"` returned HTTP 500; the corrected lifecycle succeeded with `key: "msgContent"`, INPUTING (`flowStatus: "2"`), 1-second waits, terminal finalize and FINISHED (`flowStatus: "3"`). This result covers that group/template path only. No private identifiers or secrets are recorded.

The [DingTalk-Real-AI SDK contract, pinned at the inspected commit](https://github.com/DingTalk-Real-AI/dingtalk-channel-sdk-python/blob/6f42d37ab22b0d872450148efe01c7b4b82d1e78/SPEC.zh-CN.md#5-ai-卡片协议五步) corroborates this public template, streaming key and states. Its spacing guidance is approximately 500ms around frames, with at least 800ms between streaming updates; the example uses 1 second. These are template/client conventions, not generic API validation or automatic scheduling in this node. SDK content-size handling differs from the API documentation above; this release does not change payload limits or add truncation.

The v0.6.0-beta.3 prerelease changed the guided Streaming Update/Finalize key default to `msgContent`; this behavior is part of the stable package. Custom template keys remain overrideable; existing saved keys and whole-body JSON are unchanged. Generic Finalize sends only a terminal streaming frame with mutually exclusive terminal flags. For visual completion of this public template, follow it with Update merging `flowStatus: "3"` and final `msgContent`. The [lifecycle payload recipe](../examples/public-ai-lifecycle.payload.json) includes the state parameters, full snapshots and waits.

## v0.2.0-beta.1 prerelease: narrow Card Stream transport

Protocol references checked 2026-10-24: [DingTalk Stream protocol](https://open-dingtalk.github.io/developerpedia/docs/learn/stream/protocol/), [card callback routing](https://open-dingtalk.github.io/developerpedia/docs/learn/card/intro/), and [official card examples / single-service constraint](https://github.com/open-dingtalk/dingtalk-card-examples#注意事项). The [official callback example](https://github.com/open-dingtalk/dingtalk-card-examples/blob/main/app/stream/card_callback_handler.py) demonstrates `content.cardPrivateData.params`. These support protocol implementation; they are not evidence of live callback E2E.

The trigger uses the existing credential and n8n `httpRequest` for `POST https://api.dingtalk.com/v1.0/gateway/connections/open`, with JSON `{clientId, clientSecret, subscriptions:[{type:"CALLBACK",topic:"/v1.0/card/instances/callback"}], ua}`. The helper has a 30-second timeout, disabled redirects and an abort signal. No access token is needed for this gateway request. Its response is private and never emitted/logged. Require nonempty ticket and a valid `wss:` endpoint without userinfo/fragment before adding ticket with `URL.searchParams.set`. Each reconnect requests a new ticket; tickets are neither cached nor persisted.

Native Node 24 WebSocket handles wire-level control ping/pong. Application SYSTEM `ping` receives `{code:200,message:"OK",headers:{messageId,contentType:"application/json"},data:JSON.stringify({opaque})}`. SYSTEM `disconnect` initiates reconnection without a callback emission. Opening times out after 30 seconds; 120 seconds without messages causes reconnection. Failure delays increase from 1 to 30 seconds and remain capped; valid ping/callback traffic resets backoff. Deactivation aborts lookup, clears timers, detaches callbacks, closes the socket and releases the module-local Client ID lock. An outstanding helper that ignores abort still cannot open a socket after stop.

For exact-type/topic CALLBACK envelopes with a message ID, first send `{code:200,message:"OK",headers:{messageId,contentType:"application/json"},data:"{}"}`, then normalize/emit one n8n item. Malformed inner data JSON remains a string; malformed envelopes are ignored. The item contains raw callback data, never the gateway response or credentials. Optional field extraction is documented in README. ACK send/emit failures are caught with generic diagnostics and reconnect; original errors/causes and server error codes/bodies are discarded. Receipt ACK cannot guarantee downstream completion or exactly-once processing.

Form Create & Deliver adds `callbackType:"STREAM"` only when Enable Stream Callbacks is true; default/false omits callbackType. Whole-body JSON remains passthrough. The listener must use the same Client ID as creation; DingTalk’s card examples require one Stream service per Client ID. The process-local lock cannot coordinate other processes/services. No HTTP callback mode, synchronous local-update ACK, persistent deduplication or downstream-dependent response exists in this prerelease. Follow ACK with normal asynchronous Update calls as needed.

Security decision: avoid the upstream SDK due the previously verified ticket-log risk; do not import/copy its implementation or patch global console. Fixed generic diagnostics intentionally discard connection/gateway errors even if they contain apparently useful codes. Native construction, handshake errors and pending/active shutdown are covered with sentinel secrets and real local TLS subprocess tests. The tracked-timer lint exception exists because pinned n8n-workflow 2.44.2 has no exported `sleepWithAbort`; plain `sleep` cannot cancel these lifecycle timers.
## Trigger callback normalization

The Trigger preserves its existing top-level callback fields and adds the versioned `normalized` envelope. Existing workflows require no migration to keep using those fields. See the [v1 interaction contract](INTERACTIONS.md). The **Include Raw Callback Data** option defaults to true; disabling it removes only top-level `rawData` and reduces duplicate serialization, not sensitive content.
